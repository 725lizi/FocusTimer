## 2. 时间口径（先看这一节，否则数字对不上）

| 项 | 值 |
|---|---|
| 锚点「现在」 | `2026-11-13 18:00`（UTC+8，周五） |
| `NOW_MS` | `1794564000000` |
| A 的 7 天窗口 | `[1793959200000, 1794564000000]` 即 `2026-11-06 18:00 ~ 2026-11-13 18:00` |
| B 的 30 天窗口 | `[1791972000000, 1794564000000]` 即 `2026-10-14 18:00 ~ 2026-11-13 18:00` |

- **时间戳固定按东八区换算**，脚本不读系统时钟、不用随机数：在任何机器、任何时区运行，生成的
  `startTime` 与文件内容都逐字节相同（已用 SHA256 对重复运行做过校验）。
- 引擎用 `new Date(startTime).getHours()` 取**设备本地小时**来决定所属时段，因此本数据请在
  **UTC+8 环境**查看；换到别的时区，6 个时段的分布会整体平移（`startTime` 本身不变，这是引擎既定口径）。
- 统计口径（与 `FocusProfileStats.ets` 完全一致）：按 `startTime` 归属窗口与日期、
  **一条记录不跨日拆分**、时段按**开始小时**归属整条时长、多标签时长**均摊**、数值保留 1 位小数。

### 4.4 周际变化复算（引擎口径）

引擎比较的是 `allSessions` 里两个区间（注意是**不限窗口**的全部记录）：

- 最近 7 天：`(NOW−7d, NOW]` → 11-06 18:00 之后开始的记录 = A 的 21 条 = **1276 分钟**

- 变化 = (1276 − 580) ÷ 580 × 100 = **+120.0%**

> 这是**这份合成数据的算术结果**，只用于演示「周际变化」这条事实/洞察的展示效果，
> 不代表任何真实效率变化，也不能据此推断任何因果。

## 7. 极端值敏感性（为什么 63.4% / 56.2% 这么高）

A 里那条 485 分钟的记录（`demo-20261108-02`）是**故意**做成「计时未停止」的产物
（它覆盖 09:15→17:20，与当天的 13:05、15:30 两条记录时间重叠，这正是异常的特征）。
引擎的既定口径是「保留 + 在 calcNote 标注，不静默丢弃」，所以它会完整进入统计。

把它剔除后重新 `build`（20 条 / 791 分钟）的实际结果：

| 指标 | 含极端值 | 剔除极端值 |
|---|---:|---:|
| 条数 / 总时长 | 21 / 1276 | 20 / 791 |
| 单次均值 | 60.8 | **39.6** |
| 单次中位数 | 38 | **36.5** |
| 主导类别 | 高数 63.4% | 高数 **41.0%**（仍是第一） |
| 最高时段 | 上午 56.2% | 上午 **29.3%**（仍是第一，晚间 27.8% 紧随） |

结论：**主导类别与高频时段这两条结论在剔除极端值后依然成立**，只是占比数值被极端值放大；
中位数几乎不受影响（38 → 36.5），这也是引擎用中位数抵抗极端值的直观演示。

## 8. 如何复现与自检

**重新生成（确定性）**

```bash
python demo_data/make_demo_sessions.py
```

- 无随机数、不读系统时间；重复运行输出逐字节一致（可自行 `sha256sum` 比对）。
- 脚本末尾会打印 7 天 / 30 天两份统计报告，并与本文件的数字一致。
- 脚本内置**设计自检**（`validate()`）：会检查“7 天跨满 7 个日期”“稀疏天/密集天数量”
  “6 个时段全覆盖且上午最高”“短/中/长/极端时长齐备”“2 条中断、2 条空标签、1 条多标签”
  “类别与时段占比和在 99.5~100.5”“30 天周际变化 = 120”“7 天记录是 30 天记录的子集”等；
  一旦数据被改动导致设计失效，脚本会直接报错退出，避免文档与数据脱节。

**用真实引擎自检（不部署设备）**

把 `demo_sessions.json` 读成 `StudySession[]`，以 `now = 1794564000000` 调
