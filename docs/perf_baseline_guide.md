# FocusTimer3 性能「优化前基线」测量手册（新手照做版）

> 目的：**只测量、不改代码**，把现在的启动耗时 / 内存 / 帧率记下来当“优化前”对照。等 10 月做完优化，再用**完全一样的步骤**测一遍，得到“优化后”，两列一减就是可写进简历的量化成果。
> 测的时间：2026-09（阶段 4 收口后第一次基线）。

---

## 0. 测前先看这 5 条（很重要）

1. **Profiler 只能用真机，模拟器用不了（官方硬性限制）**：华为官方明确「DevEco Profiler 仅支持 USB/无线连接的真机，不支持模拟器」。所以在模拟器上设备下拉会一直显示 No Devices、Launch/Allocation/Frame 点不了，这不是故障，换真机即可。**首选借一台 HarmonyOS NEXT 真机测**（数据能写进简历）；实在借不到，再用第 8 节的 hdc 命令行兜底方案在模拟器采“参考值”（口径不同，投递前仍建议补真机）。
2. **前后口径必须一致**：这次怎么测（debug 还是 release、什么设备、测多久），10 月优化后还怎么测，否则两列数字没法比。**基线建议固定用 debug 包**（你平时 Run 的就是）。
3. **每个指标测 3 次**，取中位数（3 个数排序取中间那个），避免偶发抖动。
4. 测之前：把电脑/手机上其他大应用关掉；App 每次测启动前先从后台划掉（保证是**冷启动**，即从零打开，不是从后台恢复）。
5. 先记好环境信息：设备型号、系统版本、DevEco Studio 版本、包类型(debug)。

## 1. 怎么打开 Profiler（三种方式任选）

- 顶部菜单 `View → Tool Windows → Profiler`；或
- 点 DevEco **底部工具栏的 Profiler**；或
- 双击 Shift（或 Ctrl+Shift+A）搜 “Profiler” 回车。

打开后，在左上角依次选好：**设备 → 你的应用（com.example...focustimer3）→ 主进程**。

## 2. 指标一：启动耗时（用 Launch 模板）

**看什么**：从点图标到首页能交互要多少毫秒，以及耗在哪个阶段。

步骤：
1. 先把 App 从后台划掉（保证冷启动）。
2. Profiler 主界面“新建任务”区点 **Launch** 模板 → `Create Session`。
3. 按提示**启动应用**（它会自动拉起；若没拉起就手动点一次 App 图标），让它完整进到计时首页。
4. 录到首页稳定后点停止。时间轴上会显示启动各阶段耗时：
   - 重点看 **Application 初始化、UIAbility 的 `OnCreate` / `OnForeground`（页面加载到前台）** 这几段，以及**总启动时长**。
5. 把“总启动耗时”和最长的那一阶段记下来。重复 3 次。

> 名词：**冷启动**＝进程从零创建（最慢、最常考）；与之相对的“热启动”是从后台恢复，这次只测冷启动。

---

## 3. 指标二：内存（用实时 Memory 泳道 / Allocation 模板）

**看什么**：App 静止时占多少内存；你操作一圈、回到首页后能不能降回去（降不回去才可能是泄漏）。

步骤：
1. 选 **Allocation** 模板（或直接用实时监控里的 **Memory 泳道**）→ Create Session，开始录制。
2. **场景 A 静止**：进到计时首页，静置 10 秒不操作，记此时内存值（看 Memory 曲线纵坐标，单位 MB）。
3. **场景 B 操作一圈**：依次 进统计页 → 打开 AI 周报 → 进知识库 → 重建一次索引 → 提一个问题 → 一路返回首页。
4. 回到首页后再静置 10 秒，记此时内存值。
5. 重复整套 3 轮，每轮都记“操作前 / 操作后回首页”两个值。

> 怎么判断：操作后内存短暂升高是正常的；**回到首页静置后应明显回落、且多轮后不会一轮比一轮高**。如果每轮基线都往上爬、不回落，才是需要优化的泄漏信号（这正是 10 月要优化的点）。

---

## 4. 指标三：帧率 / 卡顿（用 Frame 模板）

**看什么**：滑动列表、页面切换时掉不掉帧，平均 FPS 多少、卡顿帧(Jank)有几个。

步骤：
1. 选 **Frame** 模板 → Create Session 开始录制。
2. 在**统计页 / 笔记列表 / 知识库问答记录**这些内容较多的页面，用鼠标（真机用手指）**匀速上下滑动约 10 秒**，再做 2~3 次页面跳转。
3. 停止后，**用鼠标在 Frame 泳道框选刚录的这段**：
   - 子泳道 **App Frame / RS Frame** 上会出现 **FPS**（帧率，越接近 60/120 越流畅）；
   - 下方 **Statistics** 里看 **Jank Count（卡顿帧数）**，理想是 0 或很少。
4. 记“平均 FPS + Jank Count”，重复 3 次。

> 名词：**FPS**＝每秒渲染多少帧，60Hz 屏幕满帧是 60；**Jank（卡顿帧/丢帧）**＝某一帧没在规定时间画出来，表现为滑动一顿。

## 8. 借不到真机时：hdc 命令行兜底（模拟器可做，由助手代跑）

> 前提：模拟器已启动、App 已安装。下面命令走 hdc（DevEco 自带调试桥），不需要 Profiler。**这些可以直接让助手执行，你只需在模拟器里按提示操作 App。**

### 8.1 内存（可在模拟器采，反映相对趋势）
- 实际物理占用看 `/proc/<pid>/status` 的 **VmRSS**，历史峰值看 **VmHWM**，单位 kB（÷1024 得 MB）。
- 流程：App 停在首页静置 → 采一次 VmRSS；在 App 里“走一圈”回首页静置 → 再采一次；重复 3 轮，看是否回落、是否逐轮抬高。
- 参考命令（助手执行）：
  ```bash
  hdc shell "ps -ef | grep focustimer | grep -v grep"      # 找 PID
  hdc shell "grep -E 'VmRSS|VmHWM' /proc/<PID>/status"     # 读内存
  ```

### 8.2 冷启动耗时（命令行可测，Profiler 反而不支持冷启动采集）
- 先强制停 App，再用 `aa start` 拉起并配合 `hitrace`/日志时间戳得到冷启动时长，重复 3 次。
- 参考命令（助手执行）：
  ```bash
  hdc shell "aa force-stop com.example.focustimer3"
  hdc shell "aa start -a EntryAbility -b com.example.focustimer3"
  ```
  （精确到各阶段耗时用 hitrace 抓取，由助手解析。）

### 8.3 帧率（模拟器仅作参考）
- 模拟器帧率受电脑性能影响，**不具真机代表性**，只能同机前后对比；可用 `hidumper` 查 RenderService 的帧统计。投递前强烈建议用真机补一次 Frame 数据。

> 结论：命令行兜底能先拿到“内存 + 冷启动”的参考基线，让你明天不空手；但**写进简历的正式性能数据，最终一定要用真机 + Profiler 复测一遍**。
