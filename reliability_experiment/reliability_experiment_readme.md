# 「三级容错」故障注入样本库 · 说明（数据卡）

> ## ⚠️ 先看这段声明
>
> 1. 本目录下所有样本都是**人工合成的测试用例**，**不是真实模型输出**，也不含任何真实用户数据或隐私。
> 2. 样本里的 `expect` 标签是**逻辑判定的标准答案**（用来核对「抽取 → 规整 → 降级」这条链路判定得对不对），
>    **不是对真实模型成功率的预测，也不冒充真实成功率**。
> 3. 真实成功率只能在设备上实测得到；那部分数据不在本目录，本样本库不替代、不预示、不外推。
> 4. 本样本库只用于离线实验与回归，**不部署到设备**，不参与 App 运行。
> 5. 全部内容确定性生成：不用随机数、不读系统时钟、不联网、不需要 API Key，重复运行逐字节一致。

---

## 1. 这是什么、为什么做

「鸿端时计」的专注画像用了一条**三级容错链路**：

1. **前置结构化 Prompt**：把模型约束成只输出一个 JSON 脑图对象（固定根节点、四个一级分支、节点数 8–20、深度 2–3、叶子文案短、数字必须来自固定底稿）；
2. **JSON 鲁棒抽取 + 规整**：先从不干净的文本里挖出 JSON（去 markdown 围栏、去前后口语、截首尾大括号），再按确定性规则修复（补 id、补 children、截断超长文本）；
3. **本地规则树兜底**：不调模型，用同一套契约在本地拼出一棵合规脑图，保证功能永远有产出。

要做 G0–G3 消融实验，第一步需要一个**离线的、脏得有代表性的**「模型原始响应」样本库：
它能覆盖各类真实会遇到的脏数据与网络错误，并且每条都提前写清「标准答案」，这样每一级处理逻辑的判定对错可以逐条比对。

**这个样本库不产出任何关于真实模型能力的结论**，它只是给链路做单元级的对照表。

## 4. 样本字段说明

### 4.1 内容类（`kind = "content"`，共 60 条）

```json
{
  "_model": "DeepSeek",
  "id": "S01",
  "batch": "structured",
  "kind": "content",
  "case_type": "clean",
  "raw": "模型原始响应文本（含围栏/口语/脏数据就照实写）",
  "expect": {
    "g0_parse": true,
    "g1_contract": true,
    "g2_outcome": "direct",
    "g3_source": "llm"
  }
}
```

| 字段 | 含义 |
|---|---|
| `batch` | `bare`＝裸模型（无结构化 Prompt 约束，输出更脏）；`structured`＝结构化 Prompt 后（更规范） |
| `case_type` | 这条样本具体模拟哪种场景（见 §6） |
| `raw` | 模型原始响应文本，脏数据照实写（不美化） |
| `expect.g0_parse` | 对 `raw` 只做裸 `JSON.parse` 是否成功 |
| `expect.g1_contract` | `raw` 是否**未经修复**就满足**理想软 Schema**（根 id/text、四分支顺序、节点 8–20、深度 2–3、三字段、叶子 ≤16）。**它是独立指标，不决定降级**——可以 `false` 而 `g2_outcome` 仍是 `direct` |
| `expect.g2_outcome` | 走完 extract+normalize 后按**硬逻辑**的判定：`direct`＝零修复、能直接用；`repaired`＝修过但可用；`fail`＝修不好、要降级 |
| `expect.g3_source` | 最终来源：`llm`＝云端结果可用；`rule`＝降级本地规则树；`failed`＝连规则树都失败（正常不出现） |

### 4.2 网络类（`kind = "network"`，共 20 条）

```json
{
  "_model": "DeepSeek",
  "id": "S31",
  "batch": "structured",
  "kind": "network",
  "case_type": "timeout",
  "error_kind": "timeout",
  "http_status": 408,
  "framework_code": null,
  "expect_fallback": true
}
```

| 字段 | 含义 |
|---|---|
| `error_kind` | 归一后的错误类别：`network` / `timeout` / `unauthorized` / `rate_limited` / `server` / `bad_request` / `empty` / `cancelled` |
| `http_status` | HTTP 状态码，无则 `null` |
| `framework_code` | 鸿蒙底层框架码，无则 `null` |
| `expect_fallback` | 是否应自动降级到本地规则树；**只有 `cancelled`（用户主动取消）为 false** |

错误码映射（校验脚本会重算并核对）：

| 来源 | 取值 | 归一为 |
|---|---|---|
| HTTP | 401 / 403 | `unauthorized` |
| HTTP | 429 | `rate_limited` |
| HTTP | 400 / 404 / 422 | `bad_request` |
| HTTP | 408 | `timeout` |
| HTTP | ≥ 500 | `server` |
| HTTP | 其他 | `network` |
| 框架码 | 2300089 | `cancelled` |
| 框架码 | 2300004 / 2300047 / 2300999 | `timeout` |
| 框架码 | 其他 | `network` |
| 都没有 | — | `network` |

## 5. 判定规则（标签就是照这套规则算出来的）

**抽取（extract）**
- 空白 / 空字符串 / 只有代码围栏没有内容 → `EMPTY`
- 找不到任何大括号（无 `{` 或无 `}`）→ `NO_JSON`
- 能取到首个 `{` 到末个 `}` 之间的内容 → 抽取通过（**不判断语法**）

**规整（normalize）**
- `JSON.parse` 失败（截断、语法错误、根不是对象）→ `INVALID`
- 解析成功后的确定性修复：根 id 固定 `root`；其余节点 id 缺失或重复时按层序补 `m0/m1/...`；
  `text` 为空补默认文案、超 24 字符截断；`children` 缺失 / 为 `null` / 非数组一律补成 `[]`；
  裸根节点与 `{ "root": { ... } }` 信封都接收，最终统一输出裸根节点。
- **注意：这里没有「拍平层级」这一步。** 输入第 4 层，输出还是第 4 层，不会因为深度而报错
  （这正是 `wrong_depth` 的标签依据，见 §7）。

**降级**：除 `cancelled` 外，其余错误一律自动降级到本地规则树。

**判定分两层（决定「能不能用」和「有多理想」是两回事，详见 §7.5）**

- **硬逻辑 `structuralOk`｜真实系统强制，决定是否降级**：根节点存在；每个节点 `id` 是非空且全局唯一的字符串；
  `text` 是非空字符串且 ≤ 24 字符；`children` 一定是数组。
  **不限制深度、不限制节点数、不要求四个分支、不要求叶子 16 字。**
  真实链路 `extract → normalize → JsonSerializer.deserialize` 只在这三步任一步抛错时才降级规则树。
- **软 Schema `softSchemaOk`｜理想 Prompt 契约，只统计、不参与降级**：根 `id=root`、`text=本周专注复盘`；
  四个一级分支顺序 `总体情况 / 科目分布 / 专注质量 / 下周行动`；节点总数 8–20；深度 2–3；
  每节点只有 `id / text / children` 三个字段；叶子 text ≤ 16 汉字。

`g1_contract` 记录的是**软 Schema**（raw 不经任何修复是否就满足理想契约），
所以它和「会不会降级」**不是**同一件事：可以出现 `g1_contract=false` 但 `g2_outcome=direct`。

## 6. 两批样本的区别与配额（共 80 条）

每批 40 条 = 内容类 30 + 网络类 10。

| 批次 | 内容类 | 网络类 | 内容里 `direct` 的条数 |
|---|---:|---:|---|
| `bare`（裸模型） | 30 | 10 | **8**（配额 6–8：5 条 clean + 2 条 envelope + 1 条 wrong_depth） |
| `structured`（结构化 Prompt 后） | 30 | 10 | **19**（配额 18–20：16 条 clean + 2 条 envelope + 1 条 wrong_depth） |

> 说明：修正 `wrong_depth` 标签（§7 口径说明 ②）后，这两条从 `fail` 变成 `direct`，
> 两批的 `direct` 各 +1（7 → 8、18 → 19），**仍然落在原配额内**，没有为了凑配额改动其他样本。

**网络类 10 条的构成（两批相同）**：network 2、timeout 2、unauthorized 2、rate_limited 1、server 1、bad_request 1、cancelled 1。

> 说明：提示词锁定的这 10 条配额里不含 `empty`（返回为空）这一类——同类场景由**内容类**的 `empty`
> （raw 为空串 / 只有代码围栏）覆盖；`empty` 仍是 `error_kind` 的合法取值，
> 以后要补「网络类返回为空」的样本，按 §4.2 的字段追加一行并重跑校验即可。

> 两批的**唯一差别**就是内容类里「直接合规」的比例，用来体现结构化 Prompt 的约束作用。
> 这是**人为设定的离线测试配额**，用于验证处理逻辑，
> **不代表真实模型的真实分布，更不代表真实成功率**。

## 7. 14 个内容场景与对应标准答案

| case_type | 场景 | g0_parse | g1_contract | g2_outcome | g3_source | 说明 |
|---|---|:---:|:---:|---|---|---|
| `clean` | 完全合规的裸 JSON | ✅ | ✅ | `direct` | `llm` | 直接可用 |
| `envelope` | `{ "root": { ... } }` 信封 | ✅ | ✅ | `direct` | `llm` | 见下方口径说明 ① |
| `fence` | 被 ```json 围栏包住 | ❌ | ❌ | `repaired` | `llm` | 去围栏后可解析 |
| `chatter` | 前后有口语 | ❌ | ❌ | `repaired` | `llm` | 截首尾大括号后可解析 |
| `missing_id` | 节点缺 id | ✅ | ❌ | `repaired` | `llm` | 补 `m*` 号 |
| `duplicate_id` | 两个节点 id 相同 | ✅ | ❌ | `repaired` | `llm` | 重复的重新补号 |
| `missing_children` | 节点缺 children | ✅ | ❌ | `repaired` | `llm` | 补 `[]` |
| `wrong_children_type` | children 写成字符串或对象 | ✅ | ❌ | `repaired` | `llm` | 一律补 `[]` |
| `long_text` | 叶子文案超 24 字符 | ✅ | ❌ | `repaired` | `llm` | 硬截断到 24 |
| `missing_text` | 节点缺 text | ✅ | ❌ | `repaired` | `llm` | 补默认文案 |
| `truncated` | JSON 被截断（仍有 `}`） | ❌ | ❌ | `fail` | `rule` | 解析失败 → 降级 |
| `no_braces` | 纯文字，没有任何大括号 | ❌ | ❌ | `fail` | `rule` | `NO_JSON` → 降级 |
| `empty` | 空串 / 只有围栏 | ❌ | ❌ | `fail` | `rule` | `EMPTY` → 降级 |
| `wrong_depth` | 层级过深（第 4 层） | ✅ | ❌ | `direct` | `llm` | 见下方口径说明 ② |

**两处口径说明（重要，避免误读）**

1. **`envelope` 判 `direct`**：输出契约第 2 节**显式**要求兼容 `{ "root": { ... } }` 信封写法，
   信封属于契约认可的形态、不是脏数据，因此 `g1_contract = true`、`g2_outcome = direct`。
   （如果实现把它当成一次「解包修复」，那么这一场景应整体改判为 `repaired`——脚本按本文件的口径校验，
   改口径时需同步改 `validate_corpus.mjs` 的 `contractOk`/`deriveExpect`。）
2. **`wrong_depth` 判 `direct`（不是 `fail`）**：真实代码里 `normalize` **没有**「拍平层级」这一步，
   组件库 `JsonSerializer.deserialize` 也只校验 id / text / children，**完全不限制深度**。
   所以一棵「结构完全合法、只是深到第 4 层」的树：裸 `JSON.parse` 成功 → `extract` 成功 →
   `normalize` 成功且**零修改**（深度原样保留）→ `deserialize` 成功；
   真实系统会把它当云端结果**直接显示**，**不会**降级。它不满足的是**理想软 Schema**（深度本该 2–3），
   而不是硬降级条件——所以 `g2_outcome=direct`、`g3_source=llm`，而 `g1_contract=false`。
   （这条此前被误标成 `fail`/`rule`，与真实实现矛盾，已按源码修正；两类指标的区别见 §7.5。）

### 7.5 硬逻辑 vs 软 Schema：为什么两个指标必须分开

| | 硬逻辑 `structuralOk` | 软 Schema `softSchemaOk` |
|---|---|---|
| 谁在管 | 真实代码（`normalize` + `JsonSerializer.deserialize`） | 理想 Prompt 契约（提示词里写的规范） |
| 查什么 | id 非空唯一、text 非空且 ≤24、children 是数组、根存在 | 再加：根 id/text、四分支顺序、节点 8–20、深度 2–3、三字段、叶子 ≤16 |
| 不通过会怎样 | 降级到本地规则树（`g2=fail`、`g3=rule`） | 什么都不会发生，照常显示（仍是 `llm`） |
| 对应哪个指标 | **最终可用率**：链路有没有产出（云端或规则树兜底） | **Schema 通过率**：产出离理想契约有多远 |

通俗地说：

- **硬逻辑**回答「这份输出会不会把功能搞崩」。只要 id / text / children 这三个字段站得住，
  组件库就能把它渲染成脑图——深度深一点、节点多一点、只有三个分支，都能显示，没理由降级。
- **软 Schema**回答「这份输出有多符合最初的要求」。四个分支、深度 2–3、叶子别超 16 字，
  这些没做到会影响美观和可读性，但不影响能不能用。

所以同一个样本可以「能用但不理想」：`wrong_depth` 就是 `g2_outcome=direct`（能用、零修复）
+ 软 Schema 不通过（深度 4，不理想）。这正是把
「**最终可用率**」和「**Schema 通过率**」拆成两个指标的原因：前者衡量兜底链路有没有守住
「永远有产出」，后者衡量云端输出离理想形态有多远。混成一个数字，要么高估质量、要么低估可用性。

本库这两个数字（只描述这 60 条**合成用例**，不代表真实模型）：

- 最终可用率 **100%**（60/60：失败一律降级规则树，不会出现 `failed`）
- Schema 通过率 **78.3%**（47/60，未通过的 13 条见 §9 的实际输出）

## 8. 校验脚本做了什么

`validate_corpus.mjs` 只做两个层次，都不联网：

**第一层：照单核对**
- 四个文件是否都在；JSONL 每行是否都是合法对象；id 是否形如 `S01`/`B01` 且唯一；总数是否 80、每批是否 40；
- 字段是否齐全、枚举是否合法（`batch`/`kind`/`case_type`/`g2_outcome`/`g3_source`/`error_kind`）；
- 标签是否自洽：`direct` ⇒ `g0_parse=true`（裸 `JSON.parse` 必须成功；**不再要求 `g1_contract=true`**，因为 `g1` 是独立的软 Schema 指标）；`repaired` ⇒ `g3_source=llm` 且 `g1_contract=false`；`fail` ⇒ `g3_source=rule`；网络类除 `cancelled` 外 `expect_fallback` 都为 true；
- 两批是否都覆盖全部 14 个内容场景、`direct` 比例是否落在配额内、网络类 7 个错误类别的条数是否与配额一致；
- 内容样本出现的数字是否都在 `summary_fixture.json` 里。

**第二层：逻辑复算（这一层才是真正有价值的）**
- 按 §5 的规则**重新推导**每条的 `g0_parse` / `g1_contract` / `g2_outcome` / `g3_source`，
  和样本里写死的 `expect` 逐项比对——标签写错、raw 与 case_type 不匹配都会被当场抓出来；
  其中 `g2`/`g3` **只按硬逻辑推导**（深度、节点数、分支都不参与降级判定）；
- 网络类按 HTTP/框架码映射表重算 `error_kind`；
- 另外**单独统计软 Schema 通过率**（通过条数 / 60）并打印未通过的 id 清单，该指标不影响 `g3`；
- `clean` 场景额外要求同时满足硬逻辑与软 Schema（`clean` 的字面含义就是「完全合规」）。

任一不符 → 打印具体 id 与原因，并以非零码退出。

```
网络类              20（应自动降级 18 / 不降级 2）
--------------------------------------------------------------------
结构化成对比例控制  structured direct 19（配额 18–20） / bare direct 8（配额 6–8）
--------------------------------------------------------------------
全部校验通过：80 条样本、14 类内容场景、7 类网络场景，
四个预期标签均已按「extract → normalize → 硬逻辑」逐条复算一致。
```

### 校验脚本本身也做过反向测试

「永远通过」的校验器没有价值，所以做过 **8 组**故意破坏（改标签、塞底稿外数字、写错错误码映射、
删一条样本、破坏 JSON 行、写非法枚举、让 clean 样本不满足软 Schema、**把 `wrong_depth` 改回 `fail`**）：
**8 组全部被捕获并以退出码 1 结束**，报错都定位到具体 id，例如：

```
✗ [S02] 出现底稿之外的数字 45（允许：150/100/50/3/2/1/80/40/30/0）
✗ [S31] error_kind 标为 timeout，按 HTTP/框架码映射应为 network
✗ [B28] case_type=wrong_depth 的 g2_outcome 标为 "fail"，复算结果是 "direct"
✗ [S02] clean 样本未通过软 Schema（叶子 16 字 / 节点数 / 深度 / 四分支）
```

其中第 4 条正是这次修正的**回归护栏**：以后谁再把层级问题当成降级条件，校验会立刻报错。

## 10. 怎么复现

- 所有样本都是静态文本：没有随机数、不读时钟、不联网、不读环境变量，因此
  **同一份文件在任何机器上逐字节一致**，`node validate_corpus.mjs` 的输出也一致。
- 若要新增/修改样本：改 `fault_corpus.jsonl` 对应行（或按同样规则重新生成整份文件），
  同步检查 `expect` 标签，然后重跑校验脚本；脚本会兜住绝大多数标错的情况。
- 若要改口径（例如把 `envelope` 改判 `repaired`，或把某类场景从硬逻辑挪到软 Schema），
  需同时改本文件 §7 / §7.5 与 `validate_corpus.mjs` 里的 `structuralOk` / `softSchemaOk` / `analyze`，
  再重跑校验。

## 11. 边界

- 本样本库**不部署设备**、不被 App 引用，只作实验素材与回归基线。
- 不包含任何真实用户数据；文本内容全部是围绕一份合成周摘要底稿写的测试文案。
- 样本数量与比例是**人为编排**的测试配额，不能用来估计真实模型的成功率、错误率或分布。
- 真实成功率请在设备上用真实请求实测统计；那份数据与本目录无关，也不能用本目录替代。

## 12. G0–G3 消融实验脚本（`ablation_g0g3.mjs`）

> 本节是在原有内容之后**新增**的，前面 11 节的口径与结论都不变。
> 另外补记：本节新增了 4 个文件（§2 的清单写在消融脚本之前，故在此补上）——
> `reliability_engine.mjs`（共享判定模块）、`ablation_g0g3.mjs`（消融脚本）、
> `ablation_results.json` 与 `ablation_table.md`（脚本产物）。

### 12.1 为什么要有它

前三节只证明了「样本库写对了」，但没法回答老师要的那个问题：
**每一级容错到底救回了多少？** 所以做一次消融：固定同一份任务集（`fault_corpus.jsonl` 的
60 条内容样本），逐级叠加处理环节，看每一级的成功率怎么变。

### 12.2 四级怎么定义（同一份 60 条，逐级叠加）

| 级 | 处理 | 成功怎么算 |
|---|---|---|
| **G0** 模型直出 | `raw` 直接裸 `JSON.parse`，不做抽取/规整/兜底 | 解析成功，且结果是含 `children` 数组的对象 |
| **G1** 结构化 Prompt | 仍只裸 parse（**不加任何本地处理**），对比 `structured` 与 `bare` 两批 | 两个指标：原始可解析率、裸 parse 后天然满足软 Schema 的比例 |
| **G2** 加解析校验 | `extract → normalize → 硬逻辑 structuralOk`，**本层没有兜底** | `direct` 或 `repaired` 即成功；失败就是失败，不接管 |
| **G3** 完整三级机制 | G2 失败的样本交给本地规则树兜底 | `direct + repaired + 规则兜底` 为可用；兜底也失败才记 `failed` |

规则树不是凭空写的：`reliability_engine.mjs` 里的 `buildRuleTree` 是
`services/ai/RuleMindMapBuilder.ets` 的**逐条移植**，数字全部读自 `summary_fixture.json`。
脚本会顺带自检这棵树（19 个节点 / 深度 3 / 硬逻辑通过 / 软 Schema 通过）。

### 12.3 怎么跑

```bash
cd reliability_experiment
node ablation_g0g3.mjs
```

- 控制台打一张四级对比表 + 每一级的分解（失败构成、修复贡献、兜底率）；
- 落盘 `ablation_results.json`（机器可读，含每条样本在四级的判定）与
  `ablation_table.md`（人读表格，数字与 JSON 一致）；
- 退出码 `0` 表示自检通过；若出现「G2 失败却标成 llm」这类矛盾，会打印并 `exit 1`。

脚本结尾还会做一次**口径自检**：把这 60 条的判定结果与样本库里写死的 `expect` 逐条比对，
当前是 **60/60 一致**——因为它和 `validate_corpus.mjs` 共用同一个 `reliability_engine.mjs`。

### 12.4 实测结果（合成数据，**只描述这 60 条用例**）

| 级 | 处理 | structured | bare | 合计 |
|---|---|---|---|---|
| G0 | raw 直接 parse（可用） | 23/30 76.7% | 16/30 53.3% | 39/60 65.0% |
| G1 | + 结构化 Prompt（软 Schema 合规率） | 18/30 60.0% | 7/30 23.3% | 25/60 41.7% |
| G2 | + 抽取/规整/硬逻辑（可用） | 27/30 90.0% | 24/30 80.0% | 51/60 85.0% |
| G3 | + 规则树兜底（最终可用） | 30/30 100% | 30/30 100% | 60/60 100% |

读法（都只是这 60 条用例的算术结果）：

- **结构化 Prompt 的贡献**：同样的判定逻辑，`structured` 批的可解析率 76.7% vs `bare` 53.3%（+23.3 pp）；
  天然合规率 60.0% vs 23.3%（+36.7 pp）。说明「输入变规范」省掉的是后面一大段修复工作。
- **本地修复的贡献**：G2 把可用率从 65.0% 拉到 85.0%；`repaired` 里有 **8 条**是 G0 原本失败、
  被抽取/规整救回来的（fence 4 条 + chatter 4 条）。
- **兜底的贡献**：G2 仍有 9 条修不好（truncated 3 / no_braces 3 / empty 3），
  规则树全部接住，**最终可用率 100%、兜底率 15.0%**，最终来源 llm 51 / rule 9。
- **软 Schema 通过率 47/60（78.3%）**（与 `validate_corpus.mjs` 打印的一致），
  它和「可用率」是两回事，见 §7.5。

### 12.5 反向验证（脚本不会「永远 100%」）

故意让规则树对第一条兜底请求失败（在临时副本里注入 `return null`）后再跑，
输出如实变成：`规则兜底 8 / failed 1`、**最终可用率 98.3%（59/60）**、兜底率 13.3%，
`structured` 那一列掉到 29/30 96.7%。说明这个 100% 是算出来的，不是写死的。

### 12.6 这些数字的边界（必须一起读）

1. 本脚本只算**离线可复现**的：原始可解析率、软 Schema 通过率、最终可用率、兜底率、三类结果分布。
2. **事实一致率**（生成内容与底稿数字是否相符）**不在**本脚本，由下一步的独立核查脚本负责。
3. **p50/p95 延迟、真实模型成功率**必须用真实 API 在设备上实测，本脚本**一律不计算、不预估、不外推**。
4. 全部为合成数据，样本量与故障比例是人为编排的测试配额，
   **不能**用来估计真实模型的任何比率；G0–G3 的差值只说明「这套用例上各级补了什么」，不是真实世界的提升幅度。

### 12.7 改动说明（不影响原有结论）

为了让校验脚本和消融脚本共用一套判定，把 `extract / normalize / structuralOk / softSchemaOk /
规则树` 抽到了新文件 `reliability_engine.mjs`，`validate_corpus.mjs` 改为 `import` 它
（本地那份重复实现已删除）。重构后重跑 `node validate_corpus.mjs`：
**输出与重构前逐行完全一致、退出码仍为 0**，8 组反向破坏测试也仍然全部被捕获。
